# Scoring Simulator and Regression Tests Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Add a Host-side scoring simulator that shows CalculationTrace for hypothetical inputs, saves regression test cases in tournament configuration, reruns them on scoring-rule changes, and blocks ConfigVersion application unless changed expectations are explicitly approved.

**Architecture:** Extend the existing pure scoring engine with a participant-generic ranking API and a standard multi-round scenario runner. Store scoring test cases inside `TournamentConfigSnapshot` and a normalized IndexedDB table so they travel with immutable ConfigVersions and backups. The Host configuration editor delegates simulation/test-case UI to a focused `ScoringSimulatorPanel`, while `ConfigRepository.apply` enforces the regression gate independently of UI.

**Tech Stack:** TypeScript, React, Vitest, Testing Library, Dexie/IndexedDB, existing Vite toolchain. No network services or new runtime dependencies.

**Spec:** `docs/superpowers/specs/2026-08-19-offline-score-management-design.md`

## Global Constraints

- Raw Result + ScoringProfile remains canonical; calculated scores are derived.
- CalculationTrace is generated by the same scoring engine used by simulation and later real-result screens.
- Ties such as `1, 1, 3, 4` are valid and use the configured TieRule.
- Saved scoring test cases are tournament configuration and therefore versioned with ConfigVersion and included in backup/config transfer later.
- A scoring-rule change that changes a saved expected result is blocked by default.
- Each changed test case may be explicitly approved as an intentional change; approval updates its expected output in the same new ConfigVersion.
- Scoring profiles and saved test cases remain data-driven; do not add arbitrary formula execution.
- This phase covers standard rank-point scoring and standard aggregation. Dedicated SPECIAL/CUSTOM competition calculators remain separate follow-up work.
- Existing Result/Revision, QR/ACK, and tournament configuration behavior must remain green.

## Acceptance Gate

Phase 4 is ready for merge only when CI proves all of the following:

- A Host can enter hypothetical rank-point inputs and see calculated rank, award score, aggregate score, and CalculationTrace without creating real results.
- Tie handling uses the same engine as production scoring and shows the exact occupied-place averaging formula.
- Multi-round SUM/AVERAGE/FINAL_ONLY/BEST_N standard aggregation is deterministic and traced.
- A simulator scenario can be saved as a named scoring regression test in TournamentConfigSnapshot.
- ConfigVersion persistence keeps old expected outputs immutable.
- A scoring change that alters any saved expected output is rejected by `ConfigRepository.apply` without explicit approval.
- Every failing test must be individually approved; partial approval cannot bypass the gate.
- INVALID saved tests cannot be approved and always block apply until corrected.
- Approval updates expectations in the new ConfigVersion and records operator/time metadata.
- Existing Phase 1 Result/Revision, Phase 2 QR/ACK, and Phase 3 configuration tests remain green.
- `npm ci`, all Vitest tests, TypeScript typecheck, and production Vite build succeed.
